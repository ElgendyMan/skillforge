# خطة إعادة تنظيم واجهة SkillForge دون تغيير الوظائف

## الهدف

إعادة تنظيم واجهة SkillForge لتقليل التزاحم البصري والحمل المعرفي، وتطبيق Progressive Disclosure، مع الحفاظ الكامل على كل الأزرار والروابط والقوائم والنوافذ والإعدادات والـ workflows والـ APIs والـ business logic والصلاحيات الحالية. لن يتم تعديل قاعدة البيانات أو الـ backend أو عقود tRPC.

## ما تم فهمه من الوضع الحالي

التطبيق يستخدم React 19 وTailwind 4 وWouter وDashboardLayout موحدًا للواجهات الداخلية. قوائم الأدوار الحالية هي:

| الدور | العناصر الحالية | اتجاه إعادة التنظيم المقترح |
|---|---|---|
| المرشح | لوحة المرشح، اكتشف الاختبارات، طلباتي، التنبيهات، ملفاتي المؤمنة، ملفي المهني | إبقاء اللوحة والاكتشاف والطلبات كتنقل أساسي؛ تجميع التنبيهات والملفات والملف المهني داخل مجموعة حساب/المزيد مع بقاء كل مسار قابلًا للوصول |
| الشركة | لوحة الشركة، اختبار جديد، المحاولات، مقارنة المرشحين، اختباراتنا، ملف الشركة، التنبيهات، ملفات المراجعة | إبقاء اللوحة، إنشاء اختبار، المحاولات، المقارنة كإجراءات أساسية؛ تجميع اختباراتنا وملف الشركة والتنبيهات والملفات في مجموعات إدارة/المزيد |
| المشرف | الإشراف، سجل المحاولات | إبقاء العنصرين ظاهرين لأن عدد الوظائف محدود ولا يوجد تزاحم حقيقي |

ستُراجع كل الصفحات داخل Platform.tsx وAssessmentEnhancers.tsx وCompanyComparisonExperience.tsx وHome.tsx، وليس القائمة الجانبية فقط، لتحديد الأزرار الثانوية والمتقدمة داخل كل شاشة.

## مراحل التنفيذ

### المرحلة الأولى: تدقيق واجهة كامل وبناء خريطة العناصر

سأحصر كل route وكل صفحة وكل زر وكل dropdown وdialog وtab وfilter وsearch وform وstate ومكان استخدامه. سأربط كل عنصر بوظيفته، واستدعائه الحالي، وحالته، ودرجة أهميته، والتصنيف المقترح، ومكان العرض الجديد. ستُحفظ الخريطة في ملف توثيقي داخل المشروع قبل بدء التعديل، لتكون مرجعًا لاختبارات عدم فقدان أي خيار.

سيشمل التدقيق حالات loading وempty وerror وdisabled وpending، إضافة إلى state الخاص بالبحث والفلاتر والتبويبات ومدخلات النماذج، حتى لا يؤدي النقل البصري إلى إعادة ضبط البيانات أو فقدانها.

### المرحلة الثانية: إعادة تنظيم الغلاف والتنقل فقط

سأطوّر DashboardLayout وPortalShell بصريًا دون تغيير قيمة أي path أو طريقة استدعاء أي صفحة. سيتم تقديم مجموعات تنقل واضحة مثل الأساسي، إدارة العمل، الحساب، والمزيد بحسب الدور، مع الحفاظ على labels الحالية داخل القوائم الفرعية. سيتم استخدام Accordion أو Dropdown/More مناسب حسب المساحة، مع إبقاء حالات active وkeyboard focus وtooltips وmobile drawer سليمة.

لن تُحذف أي route. إذا نُقل عنصر من المستوى الرئيسي إلى مجموعة ثانوية، سيظل بنفس الرابط ونفس الـ onClick ونفس النتيجة، وسيُضاف اختبار يثبت إمكانية الوصول إليه من القائمة الجديدة.

### المرحلة الثالثة: تنظيم إجراءات الصفحات الداخلية

سأعيد ترتيب أفعال الصفحات داخل PageHeader وsections الحالية. ستظل الإجراءات الأساسية مثل إنشاء اختبار، بدء الاختبار، الحفظ، البحث، التصفية، المقارنة، التشغيل، الإرسال، والتصدير واضحة. أما الأفعال الأقل تكرارًا مثل اختيار الأعمدة، حفظ قوالب الفلاتر، فتح الأدوات الثانوية، وإجراءات الإدارة، فستُجمع داخل More أو Settings أو Accordion دون تغيير handlers أو mutation inputs.

سيتم الحفاظ على النماذج والـ dialogs والـ dropdowns الموجودة، مع تغيير موضع العرض أو trigger فقط عند الحاجة. لن تتم إضافة feature أو API أو schema جديد؛ أي state جديد سيكون محليًا وضروريًا فقط للتحكم في إظهار/إخفاء المجموعة.

### المرحلة الرابعة: ضبط التصميم المتجاوب وإمكانية الوصول

سأختبر التنظيم الجديد على desktop وlaptop وtablet وmobile. سيتم ضبط المسافات، العرض، ترتيب الأولويات، RTL alignment، overflow، sticky mobile header، وإغلاق القوائم عند التنقل. سأحافظ على theme وdesign tokens الحالية، وأستخدم مكونات shadcn الموجودة بدل بناء بدائل متوازية.

سيتم التحقق من keyboard navigation، focus rings، labels، aria-expanded، وescape-to-close للقوائم والنوافذ. ستُراعى reduced motion، ولن تتجاوز انتقالات الواجهة مدد الحركة المعتمدة.

### المرحلة الخامسة: اختبارات عدم الانحدار والتحقق البصري

سأضيف أو أوسع اختبارات واجهة مصدرية وPlaywright تغطي كل دور، وكل مجموعة تنقل، وإظهار/إخفاء الخيارات، بقاء الروابط، عمل الأزرار، فتح وإغلاق القوائم، واستمرار الفلاتر والنماذج بعد إعادة التنظيم. لن أغيّر اختبارات backend إلا إذا احتاجت الواجهة إلى تغطية route أو contract موجودة، ولن ألمس منطق الصلاحيات.

سألتقط لقطات نهائية لكل دور على desktop وmobile، وأراجعها بصريًا للتأكد من عدم وجود قص أو overflow أو عناصر مخفية بلا طريق وصول. ستتم مقارنة المسارات والأزرار قبل وبعد عبر خريطة العناصر، مع اختبار أن كل خيار أصلي ما زال reachable وfunctional.

## ضوابط عدم التغيير

لن يتم تعديل `server/` أو `drizzle/` أو auth أو authorization أو database أو tRPC procedures أو business logic أو response contracts. لن يتم حذف أي component أو route أو control، ولن يُستبدل أي workflow بآخر. أي تعديل سيكون داخل `client/src` أو ملفات الاختبار والتوثيق، مع إبقاء handlers والـ query/mutation calls كما هي.

## معايير القبول

| المجال | معيار النجاح |
|---|---|
| الحفاظ على الوظائف | كل خيار موجود قبل التعديل موجود بعده، قابل للوصول، ويستدعي نفس handler أو المسار |
| التنقل | كل مسارات المرشح والشركة والمشرف تعمل، مع active state صحيح وعدم وجود dead ends |
| الحالة | الفلاتر والبحث والتبويبات والمدخلات لا تُفقد عند فتح/إغلاق المجموعات أو النوافذ |
| responsive | لا يوجد overflow أو تداخل على desktop أو mobile، والقوائم قابلة للاستخدام باللمس والكيبورد |
| accessibility | focus واضح، labels وaria states صحيحة، وإغلاق منطقي بـ Escape عند الحاجة |
| الاختبارات | typecheck وVitest وPlaywright والبناء الإنتاجي تمر جميعًا، مع لقطات بصرية مراجعة يدويًا |
| النطاق | لا تغييرات backend/database/auth/authorization/API/business logic |

## الافتراضات والمخاطر

الافتراض الأساسي أن المطلوب يشمل كل الواجهات الحالية وليس صفحة واحدة فقط، وأن الهوية البصرية الداكنة وRTL ستبقيان كما هما. الخطر الرئيسي هو أن بعض الخيارات قد تكون موجودة داخل صفحات lazy-loaded أو dialogs وليست ظاهرة في القائمة؛ لذلك ستتم خريطة routes والـ source قبل النقل. خطر آخر هو فقدان state عند unmount بسبب نقل مكون؛ لتجنبه سأبقي المكونات mounted عندما يلزم أو أستخدم نفس state owner، وسأغطي ذلك باختبارات تفاعل.

إذا اتضح أثناء التدقيق أن عنصرًا لا يمكن جمعه دون تغيير سلوكه أو فقدان وصوله، فالأولوية ستكون إبقاؤه ظاهرًا، تطبيقًا لقاعدة الحفاظ على الوظيفة قبل التجميل.

## التسليم المتوقع

التسليم سيكون إصدارًا جديدًا من SkillForge يحتوي على UI/UX منظمًا، خريطة عناصر وتوثيقًا مختصرًا، اختبارات عدم انحدار، ونتائج تحقق واضحة. لن يتم إنشاء أو تعديل أي backend أو database أو authentication flow ضمن هذه المهمة.
