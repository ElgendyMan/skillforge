# SkillForge → Lovable / Supabase migration guide

## What this export is

This package preserves the verified SkillForge source tree and its repository-relative paths. The current runtime is React + tRPC + Express + Drizzle/MySQL with Manus OAuth, storage, and Forge services. Lovable projects normally use React/Vite with Supabase Auth, Postgres, Storage, and Edge Functions. The export is therefore a migration-ready handoff, not a claim that a MySQL server implementation can run unchanged on Supabase.

The fairness contract must survive the migration: only an authorized human reviewer may record `accepted`, `rejected`, or `under review`; scores, integrity flags, camera/screen events, recordings, and any model signal are context only.

## Recommended migration order

1. Create a new Lovable project and import the exported `client/` UI as the visual baseline. Keep the existing Arabic/RTL copy, route names, role workspaces, disclosure step, runner, review, comparison, and supervisor screens.
2. Create Supabase Auth users and a `profiles` table. Map the current `users.openId` identity to `auth.users.id` and keep an application role (`candidate`, `company`, `supervisor`) in `profiles`. Never trust a role supplied by the browser.
3. Apply the reviewed SQL baseline under `supabase/migrations/`. It is intentionally a starting point: validate every policy and add foreign keys/indexes appropriate to the final deployment before production.
4. Replace tRPC calls with typed Supabase queries or Edge Functions. Keep all ownership checks in database RLS and repeat sensitive checks in Edge Functions for mutations.
5. Move file bytes to private Supabase Storage buckets. Store only metadata and object paths in `file_assets`; use short-lived signed URLs after ownership/supervisor checks. Keep `pending` as the default security state.
6. Move privileged operations (review decisions, security-status changes, notifications, exports, and audit writes) to Edge Functions using the service role key server-side only. Never expose that key in the browser.
7. Replace Manus OAuth with Supabase Auth providers. Preserve the development-only mock session behavior only behind an explicit local-development flag; do not ship it enabled in production.
8. Port the existing Vitest and Playwright coverage. Add Supabase integration tests for RLS, snapshot immutability, appeal boundaries, private storage access, and notification idempotency before enabling real hiring use.

## Postgres conversion notes

- MySQL `int` identity columns become `bigint generated by default as identity` or `uuid`; use one consistent strategy and update client types.
- MySQL `timestamp` values become `timestamptz` and are stored in UTC.
- MySQL enums become Postgres enum types or checked text values. The baseline uses enums for security-sensitive state fields.
- MySQL `json` becomes `jsonb`.
- MySQL `varchar/text` become `text` unless a meaningful database constraint is required.
- Drizzle's `onDuplicateKeyUpdate` logic must become `insert ... on conflict (...) do update` in SQL or an Edge Function transaction.
- Add indexes for every RLS predicate (`company_id`, `candidate_id`, `attempt_id`, `user_id`) before production.

## Required RLS model

Enable RLS on every application table. Candidates can read only their own profiles, attempts, answers, disclosures, accommodations, appeals, notifications, and published feedback. Company members can read only tests, attempts, answers, recordings, comments, annotations, and exports belonging to their company. Supervisors can access the explicitly defined oversight scope. No client-side route gate is an authorization boundary.

Use helper functions such as `private.current_role()`, `private.is_company_member(company_id)`, and `private.can_access_attempt(attempt_id)` in policies. Keep these functions `security definer`, schema-qualified, and protected from arbitrary public execution. Test both positive and negative paths with two companies and two candidates.

## Snapshot and decision requirements

At attempt start, write the test version plus immutable section/question snapshots in the same transaction. Candidate and reviewer reads must prefer snapshots and must fail closed if a snapshot is missing for a newly created attempt. A review mutation must require a company membership check, a rationale, and one of the three allowed decisions. It must not derive a decision from score, priority, proctoring, or AI output.

## Storage and retention requirements

Create private buckets for evidence and recordings. Enforce size/type limits at the Edge Function boundary, validate magic bytes server-side, calculate SHA-256, and insert metadata with `security_status = 'pending'`. Only a supervisor/security workflow can transition an asset to `available`. Configure a documented lifecycle deletion job for `expires_at`; do not promise a retention period until the job is monitored.

## Supabase-specific production checklist

- Confirm Auth redirect URLs and email sender/domain.
- Review every RLS policy with a second person and automated negative tests.
- Enable database backups and test restore.
- Configure Storage lifecycle deletion and malware scanning/quarantine outside the browser.
- Keep `SUPABASE_SERVICE_ROLE_KEY`, Resend credentials, runner credentials, and any provider secrets in server-side project secrets only.
- Configure rate limits, audit-log retention, incident response, accessibility, and human-review policy.
- Verify code execution isolation, language allowlist, network egress, CPU/memory/time quotas, and artifact cleanup with the selected sandbox provider. Supabase itself is not a code sandbox.

## Known non-automatic work

The export does not silently rewrite the complete tRPC/Drizzle backend into Supabase code. The current source remains available for behavioral reference, while the SQL baseline, dependency map, and this guide define the controlled migration path. Run the source test suite before and after each slice of the migration.
